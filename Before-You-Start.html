P3

The backend, which does not exist

9 items

Everything the attestation work does is client-side evidence. Until a server checks it, none of it stops anybody — an assertion nobody verifies is theatre. Two MASVS controls stay open purely on this.

  • The certificate chain to Apple’s App Attest root, the nonce (SHA-256 of the authenticator data plus the SHA-256 of the challenge), the App ID hash against the right team and bundle ID, a counter of 0, and the aaguid. Store the receipt — it is what later lets you assess risk per key.

  • Which means storing each key’s public key at registration, so there is something to verify against.

  • A keyId is public. Acting on one without a verifying assertion lets anyone burn someone else’s rate limit by submitting their key.

    Source threat model, abuse case U5

  • Challenges single-use, stored, deleted on first use, expiring after 120 seconds. And the assertion counter must strictly increase per key, with the write transactional against issuing the token — a non-atomic update is a replay window. The counter is the half that gets forgotten.

  • Short-lived access token, 900s by default. Refresh token rotated on every use — and a refresh token presented twice means it leaked, so revoke that key’s session family and force re-attestation.

  • 10/min on /attest/challenge, 5/hour on /attest/verify, 30/hour on /session/refresh, plus a separate global limit for challenge requests that carry no key at all.

  • Apple ignores the appattest-environment entitlement once a build ships through TestFlight, so a preview build installed from TestFlight produces production attestations. Decide per environment; never infer it from the variant or the bundle ID.

  • And keep production data to the production bundle ID only.

  • Manual only, or automated on a risk signal from the attestation receipt. Also settle whether keyId becomes a data-retention subject once it is logged server-side — it is an install identifier.

Full contract docs/api/attestation.md  ·  Fake server test/mocks/attestation-handlers.ts

Settled

Decided, not forgotten

10 items

These look like gaps and are not. Each was considered and decided against, with the reasoning recorded. Do not “fix” them without reading the ADR first.

  • No simulator-specific attestation result. App Attest reports itself unavailable on the Simulator before any API can say more, and no bundled module exposes a simulator flag. Distinguishing it would mean adding expo-device to change a log label.
  • EXPO_PUBLIC_USE_RN_FETCH=1 is load-bearing. Never remove it. Expo SDK 57 otherwise replaces fetch with expo/fetch, which runs its own URLSession with no server-trust callback — so TLS pinning covers nothing. Removing this leaves an app that works, passes every test, and has no pinning at all, with nothing to notice. It is a required field in the env schema for exactly that reason. The cost is no streaming response bodies, which nothing needs.
  • No \uXXXX escapes in a regex character class. Twice, an escape like \u0000 reached disk as a literal control byte, which made git treat the source file as binary. Behaviour was identical, so the tests did not catch it. validate-deep-link.ts uses an explicit code-point loop instead.
  • No anti-obfuscation or anti-debugging (MASVS RESILIENCE-3, RESILIENCE-4). There is no secret in the bundle for it to protect, and on a device the attacker owns it is a speed bump. The defence is server-side verification.
  • The whole AUTH category is not applicable. No accounts, no sign-in, no authorization model. Revisit only if that changes.
  • The variant list is duplicated in app.config.ts and env-schema.ts. Sharing it was tried and reverted: it works under expo config --type public and breaks under --full, which is the path expo-doctor takes.
  • SQLCipher uses the passphrase form, not a raw key. The raw form skips PBKDF2 and is attractive for material that is already 256 bits, but it is outside the documented path and cannot be verified without a device.
  • There are no down migrations. A rollback on a user’s phone is a data-loss event with no operator watching. If a migration is wrong, the fix is another migration.
  • The env schema has no defaults, which is why .env is required. Defaulting the variant would let a production build that forgot it report itself as development — turning verbose logging on in a shipped app.
  • Node stays on 24 and ESLint stays on 9. ESLint 10 breaks eslint-plugin-react, which Expo’s config depends on. Three dependency pins and one patch keep npm audit at zero without leaving SDK 57.
