# ADR 0020 — Plans are generated in three verified steps

- **Status:** Accepted
- **Date:** 2026-10-05
- **Deciders:** @wwhitakerv

## Context

A plan was generated by one OpenAI request returning everything: About this
plan, every day's reading, and every day's quiz. Live runs on a real sermon
showed it fail almost every 7-day plan with Quick Check, each attempt breaking
a different rule (a passage the sermon never named, overlapping days, a day
short of verifiable quiz questions), while spending ~13,000 of a 24,000-token
budget and finishing normally. Readings came back at a quarter of the target
length: the model spread one response across ~70 quiz questions and seven days.

## Decision

`src/generation/pipeline.ts` writes a plan in three steps, each with its own
prompt (`src/generation/prompts/`) composed from the user's rules
(`prompts/rules.ts`, word for word) and its own response schema
(`src/generation/stages/`):

1. **Plan** — title, About this plan, and each day's title, focus and passage.
   Verified before anything else is written: exact day count, passages from
   chapters the sermon names, no overlapping days, text in BSB and KJV.
2. **Days** — one call per day, in parallel: reading, Scripture study,
   reflections, prayer, clip, supporting Scripture.
3. **Quizzes** — one call per day, from that day's finished reading: 9–10
   questions, mixing multiple choice and finish the verse.

A step whose output fails a check is retried on its own, up to three times,
and each retry's task lists exactly why the earlier answers were rejected
(`previousAttemptsRejected`). Days run in parallel, so repeats across days are
resolved afterwards, in day order; a day left short is rewritten with what to
avoid. Every call is recorded in `generation_attempts` (step, outcome, reason,
tokens).

**Preventing the common failures.** The server lists every chapter the sermon
names (`namedChapters`, the same matcher the check uses) and gives the list to
the plan step, so a day's passage is chosen from it rather than guessed; a
sermon that names none fails before any call. A quiz left short by questions
that fail verification keeps the ones that passed, and its retry asks only
for the missing number (`questionsNeeded`).

**Re-runs resume.** Each accepted step is saved in `generation_steps` under
what it was written from (the outline's fingerprint for a day, the day's
passage and reading for a quiz), so a retried or reclaimed job skips the steps
already done and logs them as `resumed`. The rows are deleted when the plan is
published.

**Finish the verse** is built by the server from the bundled Bible text, never
the model's memory: the model picks a verse and the phrase to blank in each
translation, and the server finds that phrase in the real verse. The answer
sits in the same position in every translation, so one set of choice ids — and
one answer key — serves all of them; `quiz_questions.variants` holds each
translation's wording, and the quiz service shows the reader's.

Each request opens with the same short preamble and the sermon and transcript,
marked as the end of a reusable prefix (`prompt_cache_breakpoint`) and keyed by
sermon (`prompt_cache_key`); the step's instructions and task follow. Every call
of a plan therefore shares one prefix: the plan call, which runs alone, writes
it to OpenAI's cache, and the days and quizzes that follow in parallel read the
transcript at the cached rate. `generation_attempts.cached_prompt_tokens`
records how much of each call's input was cached.

## Consequences

### Good

- Each step gets the model's full attention; a failure costs one step, not
  the plan.
- Quizzes test what the reader actually read.
- Every rejected call says why, with its tokens.

### Bad

- More calls per plan (1 + days + days with Quick Check); input tokens grow
  with the transcript sent to each, mostly billed at the cached rate.
- The PLAN_GENERATION_PROVIDER_URL gateway still returns a whole plan in one
  response and is checked only by the final validation.
