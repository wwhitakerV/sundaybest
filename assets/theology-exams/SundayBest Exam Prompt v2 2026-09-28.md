# SundayBest Theology Exam — THEO-01-01 implementation prompt (schema v2)

Build the Theology Exam experience in the existing SundayBest iOS app using the attached `SundayBest THEO-01-01 v2 2026-09-28.json` file. This is the sole exam content file for this handoff; do not expect or load THEO-04-03 yet. Ignore any earlier theology-exam brief that describes `options`, `correctOptionIds`, `exam.questionAllocation`, `teaching.whySelectedIsWrong`, `status`, `scoredReleaseEligible`, or a fixed four-option layout. Those fields are not in schema v2. Use the actual app architecture, navigation, theme tokens, and design system. Do not create question text, answers, explanations, or theological claims in the UI layer; render the supplied data. Keep all answer keys and explanations out of the question payload shown during an Exam Mode attempt. These are real, automatically scored exams. The JSON supplies the exact answer key, explanation, and source for each question. Do not generate, infer, or manually check answers at runtime.

## Product behavior

1. **Exam selection:** Show domain, level, title, question count, approximate duration, areas covered, and what the learner will do. This Foundations exam has 15 questions. Show source scope and a short, plain-language note that a score measures performance on these questions, not spiritual standing. A score reports performance on this exam, not a credential.
2. **Start:** Offer Exam Mode and Study Mode. Explain the difference before starting. Exam Mode scores after submission; Study Mode gives immediate teaching feedback.
3. **Question screen:** Show one question at a time, its position, stem, and passage reference links. Render the interaction specified by each item: single choice, true/false, multiple select, matching, ordering, or another fixed-answer format supplied by the JSON. Passage interpretation and application can use any of these formats. Permit previous/next navigation and preserve selections. Do not infer an answer from display order or wording.
4. **Exam Mode:** Commit selections without correctness feedback. Let learners return to earlier questions. Show answered/unanswered progress. Submit requires explicit confirmation and identifies unanswered items; an unanswered item scores as incorrect. Reveal keys and teaching only after submission. Never put keys in pre-submission client data in a production implementation; grade in a trusted service.
5. **Study Mode:** After an answer is committed, show whether it is correct, a short reason, and an **Understand why** action. For choice and true/false questions, use each `interaction.choices[].rationale` for option feedback. For multiple select, show the full keyed set and the stored rationale for incorrectly selected options and missed correct options. For matching, show the correct mapping with `teaching.matchFeedback`; for ordering, show the correct sequence with `teaching.stepFeedback`. Study attempts do not create blind exam mastery evidence.
6. **Understand why:** Show the concept explanation, biblical grounding with openable passage links, the important distinction, and the `rememberThis` line. Use supplied source links. Keep the passage in context; do not generate or display unlicensed full passage text. Keep this reading sheet accessible from both correct and incorrect item review.
7. **Results:** Show raw score and denominator, percentage, and the provisional bands: 90–100 Mastered, 80–89 Strong, 70–79 Developing, below 70 Review Recommended. Show each question's selected answer, correct answer, explanation, and links to the reading sheet. Aggregate concept observations with a numerator and denominator; show a strength/weakness label only with at least three independent scored observations of that concept. Otherwise say **Not enough evidence**. Queue missed primary concept IDs for review.
8. **Retakes and progress:** With only one authored form per exam, label a retake **Practice**. Do not present repeated exposure to the same items as independent mastery evidence. Preserve an attempt's exam ID, item IDs and versions, mode, selections, timestamps, and result so a future edit does not silently change an earlier attempt. The app uses the predetermined answer key and explanations in the supplied JSON; it does not ask a model or a person to judge a submitted answer.

## Design direction

Use SundayBest's existing visual language: restrained editorial typography, white or paper surfaces, black or ink text, and SundayBest red `#D62626` for active emphasis. Use existing design tokens and components where available; avoid inventing a parallel design system. Keep the question itself visually dominant. Make answer controls large, calm, and easy to tap; use clear selected, committed, correct, and incorrect states that do not rely on color alone. Keep passage links close to the stem. Make progress visible without turning the experience into a game show. The reading sheet should feel like a focused study page, with comfortable line length and space to read. Use existing SundayBest navigation and its motion and reduced-motion conventions. Do not add header specifications to this body-content brief.

## Data and acceptance checks

- Read `exam`, `exam.experience`, `questions`, each item’s `interaction` and its fixed `answerKey`, `whyCorrect`, `teaching`, and `sources` from each JSON file. The JSON is the content authority. Keep the answer key private until the relevant feedback point; a trusted grading service should evaluate Exam Mode submissions.
- Verify the 15 question IDs, count, and interaction counts against `exam.questionIds`, `exam.questionCount`, and `exam.interactionAllocation` before rendering. Fail closed and show an internal content error if a required ID, key, choice/target/step, or feedback value is missing. There is no `status` or `scoredReleaseEligible` field. Their absence must not disable scoring or mark this exam as a draft.
- Read `interaction.kind` to choose the control. `single_choice` and `true_false` use `interaction.choices` and one `answerKey` ID; `multiple_select` uses choices and an array key; `matching` uses `prompts`, `targets`, and a mapping key; `ordering` uses `steps` and a sequence key. Score single choice and true/false by exact option ID; multiple select by exact set; matching by exact mapping; ordering by exact sequence. Do not give partial credit unless a later JSON explicitly defines a partial-credit rule.
- Exam Mode hides correctness until explicit submission; Study Mode reveals it after committing an answer.
- Keyboard/VoiceOver labels describe question position, selection state, and feedback; support Dynamic Type and reduced motion.
- Implement the five interaction renderers generically so the same UI can serve later exams with this schema. For this build, load only the supplied Foundations JSON. Do not auto-generate questions or substitute placeholder theology content.
